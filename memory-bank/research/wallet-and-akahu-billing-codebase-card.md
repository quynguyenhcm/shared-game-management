### TRAP Candidates
- Candidate shape "per-player OAuth connection with a stored user token, then payment API debits them" conflicts with ADR 0016's rejection of per-team credentials in spirit (adds a secret class), adds a new encrypted token table, consent/connect UX, token expiry/revocation, and has no schema or route today. Not forbidden by an ADR (ADR 0016 rules out per-TEAM, not per-PLAYER, credentials), so this is a cost flag, not a hard mismatch. Needs a new ADR if chosen.
- Candidate shape "per-team Akahu merchant id / app token" (the reserved `teams.akahu_*` columns) is a hard mismatch with ADR 0016 section "Alternatives rejected" (line 133); would require superseding the ADR.
- Candidate shape where the provider holds the payee as a pre-registered/verified "merchant" entity per team (onboarding each team with the provider) breaks ADR 0016's "payee = account name + number, no Akahu call at save time" and the `payout_blocked_at` model (a team would be un-publishable until provider onboarding completes, changing `is_payout_configured` semantics).
- Candidate shape using an Akahu-hosted payment link (no `/payments/[id]` redirect through our API) would bypass `payment_link_token`/our attempt tracking and C-BIL-PAY ordering unless the link is created under the team-row lock path; also drops our control of the return page. Flag, not a mismatch.
- Candidate shape where the destination-rejected condition is indistinguishable from payer-side failure in the provider's status codes would make R3 (`payout_blocked_at`) either never fire or fire falsely, blocking a team's paid publishing on a payer error.
- Webhook signature verification needs the raw request body; the repo has no raw-body support, so a provider whose signature covers a re-serialised/canonical JSON form (rather than the exact bytes) or that relies on fetching a rotating public key per request changes the plan (more moving parts, a cache, an outbound call in the webhook path).

### Open Questions
- Does the framing's `payment_attempts` table exist anywhere? No migration defines it; only `payments.akahu_payment_id` (single) and `credit_transactions.akahu_payment_id`. Phase 4 must add attempts and top-up intent tables (migration + ledger D-87+); their shape depends on whether the provider allows multiple payment objects per payment.
- Will the provider's webhook POST carry an `Origin` header, or originate from fixed IPs? (Origin check passes absent `Origin`; `trustProxy` is unconfigured so `request.ip` behind DO App Platform is unverified.)
- Does DigitalOcean App Platform guarantee static egress IPs if the provider requires IP allow-listing of the calling server? (ADR 0007 says vendor facts must be re-verified at deployment.)
- Is the 5 s `PROVIDER_TIMEOUT_MS` and no-retry stance in `providerFetch` acceptable for payment creation, or does payment creation need its own timeout + idempotency-key-on-retry policy? (Provider idempotency support is a docs-lane question.)
- Where does the platform-level provider webhook secret/public key live (env var vs `teams.akahu_*` reserved columns); the reserved columns are per-team and should stay unused under ADR 0016.
- Is a payment `OVERDUE` row eligible for an attempt while a previous attempt is open (task file line 65 `payment_in_progress`)? Requires an attempts table to answer.
- Do productBrief:89 / PRODDUCT-OVERVIEW §7 ("Akahu routes all payments directly to the team's account") need an amendment if the funds flow platform-account-then-payout? That would change ADR 0016's model (platform would hold funds; payout becomes a second payment).

### Compatibility Constraints
- ADR 0016: platform-level provider credentials only; no per-team credentials or merchant ids (`teams.akahu_*` stay unused); payee is the team's account name + number, decrypted in memory only (P4); no provider call at banking-save time.
- ADR 0016 R3: provider must yield a status/error distinguishable as "destination account rejected" to drive `payout_blocked_at` under `teams FOR NO KEY UPDATE`; billing never modifies banking columns.
- ADR 0016 C-BIL-PAY and lock order: `teams FOR KEY SHARE` plus `is_payout_configured` check before any payment row insert (including post-game links and, if rows are created, top-ups).
- P5/ADR 0004: no provider HTTP call under a DB lock or inside a transaction; domain write plus enqueue in one tx; handlers idempotent (at-least-once, 3 retries default, 900 s expiry).
- ADR 0009/P2: amounts exact (`NUMERIC(10,2)`/`Money`); provider amounts parsed at the adapter boundary; wallet balance cap 0..100 enforced by CHECK (`wallet.sql:8`), so a top-up of more than headroom must be rejected before the provider call and re-validated at credit time.
- P7: all provider config (base URL, app credentials, webhook secret/public key) from env, validated at boot, value-free errors; real provider refused in tests, fake refused in production.
- Webhook route: needs a new encapsulated raw-body content-type parser (none exists); must be `publicRoute()`; Origin check passes only if the request has no `Origin`; `clientAddress` is null on it; trustProxy/static egress unverified.
- Observability: outbound client must propagate `traceparent` manually (HTTP instrumentation not wired, `telemetry.ts:5-7`); never log webhook body, signature, tokens or bank values; redaction keys are global.
- Schema: single `payments.akahu_payment_id` and no attempts/top-up/webhook-event tables; provider shapes that need attempt history, top-up intents or event dedupe need new migrations (ledger D-87+, ADR 0020); `payments_guard_immutable` leaves status/paid_at/akahu_payment_id writable.
- `team_banking_in_use` considers PENDING/OVERDUE only; an in-flight provider state must map to PENDING or the removal guard must be widened by replacing that one function.
- ADR 0007: long-lived api container with TLS at edge supports a public webhook URL; static egress IPs and a public dev/CI callback URL for the sandbox are unverified.
- Product: NZ and NZD only; productBrief:89 and PRODDUCT-OVERVIEW §7 assume direct routing to the team's account (funds flow shape is a product-level assumption to confirm).
