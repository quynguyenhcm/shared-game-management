## Narrative (one paragraph)
Akahu One-Off Payments technically fit ADR 0016: a platform app token + secret, the team's account name + number passed per call, and a player redirect to Akahu's hosted `authorisation_url`, with no per-player or per-team credentials. The recommended build is a hand-written REST client (the `akahu` 2.6.0 SDK has no one-off resource), a webhook treated as a signal only (verify, persist, 2xx, re-read, guarded state-based apply, reconcile poll), and our own idempotency on create. DR-001 is a conditional ADOPT (OV-2): it holds for technical feasibility only, and Akahu's written answer on third-party payees (U1) is a go/no-go before signing the contract, accepting ADR 0020, or building the Phase 4 live adapter. A U1 negative drops DR-001 to DEFER and triggers a plan amendment (U10/U11 fallbacks, no cheap exit). Akahu documents no "destination account rejected" signal, so ADR 0016 R3 / AC-ERROR-4 has no automatic trigger and is triggered manually by ops/global admin (OV-3). The biggest remaining risks are U1 (commercial permission and liability) and BANK_ERROR_INDETERMINATE, where money may move but Akahu never reports SENT (U4), so that status needs a hold/ops branch.
