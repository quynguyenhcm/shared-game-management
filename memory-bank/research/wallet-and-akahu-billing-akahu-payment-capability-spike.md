## Research Objectives

- Establish from Akahu's current documentation whether a platform-level Akahu app can take a one-off payment from a player's NZ bank account to the team's bank account (payee = account name + number, third-party, not user-owned) without an enduring per-player connection.
- Pin down the payment status lifecycle, the webhook contract, limits, fees, sandbox coverage and the approval lead time, so the Phase 4 adapter is built against the real contract (AC-INTEGRATION-1).
- If Akahu cannot, identify which NZ pay-by-bank provider can, under ADR 0016's platform-level-credentials constraint.

## Research Questions

1. Does Akahu support a one-off payment to an arbitrary third-party NZ account from a payer who has not connected their bank, with only the platform app credential? Which product fits?
2. What is the payment status lifecycle, and which statuses or codes mean success, failure, user cancellation and "destination account rejected" (the `teams.payout_blocked_at` trigger, AC-ERROR-4)?
3. What is the webhook contract: event types, payload, signature header and algorithm, key retrieval and rotation, retries, unique event id, and does the payload suffice or must we re-read (AC-ERROR-6, AC-ASYNC-3)?
4. What are the limits, fees, sandbox capabilities, the app approval process and lead time, and any restriction on paying non-user-owned accounts or collecting for third parties?
5. If Akahu cannot do (1), which NZ pay-by-bank provider (BlinkPay, Windcave A2A, Worldline, POLi successor, others) supports a platform-held credential paying many team accounts via hosted redirect and signed webhooks?

### Challenge: DR-004 status mapping (SENT-only credit, in-flight PENDING, failures payable)
- **claim**: SENT → payment PAID once / top-up credited once; READY/AUTHORISED/SUBMITTED → attempt open, payment stays PENDING/OVERDUE; CANCELLED/* and FAILED/* → attempt closed, payment payable (B4 default); FAILED/REJECTED never sets `payout_blocked_at`; BANK_ERROR_INDETERMINATE is never auto-retried.
- **evidence**: Lifecycle doc (A; docs card row 4, DRP-001 row 4; re-fetched by this challenger 2026-10-30, digest); GetOneOffPayment ref (A, DRP-001 row 5); DRP-001 Status/Webhook Contract table; Demo Bank 5.04/5.15 (A, DRP-001 row 12); this artifact's own TRAP row "Auto-retrying, or opening a new attempt immediately after, FAILED/BANK_ERROR_INDETERMINATE" and U4/MVE-004; DR-003 ("`akahu-reconcile` sweep re-reads open attempts/top-ups"); task file AC-ERROR-3 (lines 220-223), AC-ERROR-10 (261-265), B3/B4 (447-448), Q3 (439); codebase card row 11 (`team_banking_in_use`, B) and row 9 (no top-up intent table, B); practitioner T3, T5, T9 (C).
- **challenge**:
  - *Worst failure mode (anchored, decisive).* The claim puts BANK_ERROR_INDETERMINATE in the "FAILED/* → attempt closed, payment payable" bucket. The re-fetched Lifecycle doc defines it as "it is unclear whether the payment **has or will be** processed", and states that terminal statuses "will not change after reaching this state". So if the bank did move the money, Akahu never reports SENT. Under DR-004 the attempt closes, the payment stays payable, and AC-ERROR-3 tells the player "You haven't been charged." with "Try again". The player starts a new attempt, it reaches SENT, and the payment is marked PAID once while the player has been debited twice. AC-ERROR-10's one-open-attempt guard does not stop this, because the first attempt is closed. The B3 duplicate backstop does not fire either, because only one SENT ever exists. DR-003's reconcile re-reads only *open* attempts, so nothing looks at the closed one again. The clause "never auto-retried" bans only automatic retries. A retry started by the player stays allowed, which is exactly what this artifact's own TRAP row (Auto-retrying, **or opening a new attempt immediately after**, INDETERMINATE) forbids. DR-004 as written contradicts a TRAP in the same artifact, and the correct handling is still an open Unknown (U4, MVE-004 not run).
  - *Hidden cost (anchored, non-disqualifying).* The rationale says "keeping in-flight payments PENDING keeps `team_banking_in_use` effective". That holds for payments only. A top-up in SUBMITTED is not a `payments` row, and `team_banking_in_use` counts PENDING/OVERDUE payments only (codebase B, row 11). No top-up intent table exists yet (codebase B, row 9). An in-flight top-up therefore does not hold the banking-removal guard. The payee is fixed at create (CreateOneOffPayment A), so the money still lands in the old account. This is a scope gap for Q3/migration D-87+, not a mapping error.
  - *Breaking scenario (anchored, out of scope for this claim).* SENT is terminal and there is no documented post-SENT return or reversal status (Lifecycle A; "Destination rejected: no documented code", DRP-001 contract table). If a receiving bank returns funds after SENT (for example, a closed team account), the ledger has already credited or marked PAID and nothing can unwind it. The evidence for such returns is a gap, not a finding (T3 is [SOURCE UNVERIFIED]). The Lifecycle doc defines SENT as "Payment settlement has completed", which is stronger than "initiated". So crediting on SENT remains the best-evidenced choice and this strand does not disqualify it. It belongs with U3/U13.
  - *Skeptical-senior objection (anchored, partly answered).* (a) The mapping is not total against vendor drift. T9 (C) notes that the enduring vocabulary has `PAUSED`/`DECLINED`, and the one-off OpenAPI enum (A) is closed today. The apply function needs an explicit unknown-status branch (leave the attempt open and log) rather than a FAILED/* fall-through. (b) T5 cancel/abandon ambiguity is mostly answered: CANCELLED is terminal per Lifecycle A, and the app can cancel only in READY (Cancel ref A). The remaining risk is a SENT that arrives for a locally closed attempt or an expired top-up intent. The claim does not state that SENT must be applied regardless of local attempt state. That case is routed to Q3/B3 (task file 439, 447). It is a gap, not a disqualifier.
  - *What survived.* Applying SENT only, keeping READY/AUTHORISED/SUBMITTED as PENDING/OVERDUE, mapping CANCELLED/* and FAILED/{REJECTED, BANK_ERROR, INTERNAL_ERROR} to payable, and never setting `payout_blocked_at` on REJECTED are each answered by A-grade evidence. The REJECTED rule is backed by Demo Bank 5.15 → REJECTED for payer insufficient funds.
- **disposition**: Revised
- **required_revision**: DEFER. Disqualifier: the claim's FAILED/* → "attempt closed, payment payable" catch-all covers FAILED/BANK_ERROR_INDETERMINATE. The Lifecycle doc (A, verbatim) says money may already have moved under that terminal status. Together with AC-ERROR-3's "Try again" and a reconcile that re-reads only open attempts, this lets a player pay twice without detection. It contradicts this artifact's own INDETERMINATE TRAP row, and the evidence that would settle the handling (U4/MVE-004) does not exist yet. The ADOPT cannot stand unchanged. Path back: at the Phase 4 human gate, re-admit as an explicit override only if the INDETERMINATE branch is removed from the FAILED/* bucket. That branch would keep the payment non-payable with no new attempt and flag it for ops until U4 resolves, would not show the "You haven't been charged" copy, and would add an unknown-status branch. The other clauses survived this challenge unchanged.
- **confidence note**: run on Opus (no model fallback). The Lifecycle doc was re-read via a WebFetch digest, not raw bytes.

### Challenge: DR-003 webhook handling (raw-body RSA-SHA256 verify, re-read as truth, state-based dedupe, reconcile poll)
- **claim**: "`POST /webhooks/akahu` (`publicRoute()`, route-scoped raw-body parser) verifies `X-Akahu-Payments-Signature` RSA-SHA256 over the raw bytes using the PEM from `GET /v1/webhooks/keys/{keyId}` (cached by key id, fail closed), persists + enqueues and returns 2xx within 10 s, re-reads the payment as truth, applies a guarded state-monotonic transition (no event id), and is backed by an `akahu-reconcile` poll."
- **evidence**: docs card rows 19-22 and 28 (Lifecycle, Monitoring, GetWebhookSigningKey, Enduring webhooks, Rate Limits; A, WebFetch digest); DRP-001 rows 22-26 and the Status/Webhook Contract table (A); OSS card rows 19-20 and TRAP line 31 (SDK `validateWebhook` is enduring-only, A); practitioner row 19 + T4 (C); codebase card rows 26, 33-38 (`payments_guard_immutable`, `app.ts:114-123`, `origin.ts:11-23`, `internal-auth.ts:22-48`, `policy.ts:30`, `registry.ts:12-13`, ADR 0004/P5; A/B). Re-checked by this challenger on 2026-10-30 (WebFetch digest): the Monitoring page confirms the raw payload, RSA-SHA256, "This key should be cached", "Webhooks that fail signature validation should be discarded", 2xx within 10 s with up to 20 retries, the polling fallback, and "encode state as parameters in the `webhook_uri`". It says nothing about padding, rotation, key expiry or unknown key ids, and sends readers to the enduring page for code. The Lifecycle page confirms terminal statuses "will not change after reaching this state" and defines BANK_ERROR_INDETERMINATE as "unclear whether the payment has or will be processed".
- **challenge**:
  - *Worst failure mode (anchored, answered).* The signature contract is under-specified at the byte level. PKCS1 vs PSS padding is documented only for the enduring dialect (DRP-001 row 26), and the vendor points to enduring samples (docs row 22 TRAP). A wrong padding, or a body mutated before verification, makes every genuine webhook fail closed. This does not touch correctness. The job takes truth from an authenticated `GET /v1/one-off-payments/{id}` (DRP-001 row 23), and `akahu-reconcile` sweeps open attempts (Monitoring "fallback", practitioner T4). A total verification outage therefore costs latency until the next sweep, never a wrong money state. A forged or replayed body can at most trigger a re-read of the true status, so AC-ERROR-6 rests on the re-read and the signature is defence in depth. Named check: MVE-005 (verify a captured sandbox webhook with `node:crypto`) passes before the Phase 4 build gate.
  - *Hidden cost (anchored, mitigable): attacker-driven key fetch.* "Refetch on unknown id" turns a forgeable header (`X-Akahu-Payments-Signing-Key`) into an outbound call authenticated with the platform `AppSecret` (GetWebhookSigningKey ref A). No 404 is documented for unknown ids (DRP-001 row 25). Rate limits are global, return 429 and "may change without notice" (docs row 28 A). An unauthenticated sender cycling random key ids can spend the app's shared rate budget, which starves creates and reconcile re-reads, and the id is interpolated into the request path. Binding condition: allow-list the key-id format before fetching and URL-encode it; use single-flight fetches, a negative cache and a per-window cap on key fetches; return 5xx (not 401) when the key fetch itself fails transiently, so Akahu's 20 retries can recover.
  - *Breaking scenario (anchored, not DR-003's to fix).* The claim's premise "re-read is truth" has a documented blind spot. Under FAILED/BANK_ERROR_INDETERMINATE the money may still move, but a terminal status "will not change" (Lifecycle A, re-checked). No webhook, re-read or reconcile sweep can ever observe that outcome, so DR-003 must not be credited with covering it. The fix lies in DR-004's handling and U4/MVE-004, which the DR-004 challenge revised to DEFER. No alternative webhook design closes the gap, because it sits in the vendor's state model. So it scopes DR-003 rather than refuting it. Binding condition: DR-003's caveats state that reconcile does not resolve INDETERMINATE, and the apply path routes INDETERMINATE to DR-004's hold/ops branch, not to the generic FAILED/* close.
  - *Skeptical-senior objection (anchored, answered by a guard): an unsigned correlation channel.* The Monitoring page tells integrators to put context in `webhook_uri` query params, but the signature covers only the body (Monitoring A, re-checked). A handler that picked the attempt from the URL could apply a validly signed body for payment X to attempt Y. Binding condition: resolve the attempt only by the `_payment` id stored at create (docs card open question). URL params are never authoritative, and an unknown `_payment` is a no-op. The senior's second objection, that every byte-level detail comes from a digest, is answered by MVE-005 plus the fail-safe property above.
  - *Dropped (no anchor).* "Fastify parser scope may leak to other routes": the codebase card prescribes an encapsulated plugin (row 33). "10 s is too tight": a cached-key verify plus one insert and enqueue has no evidence row against it.
- **disposition**: Upheld
- **required_revision**: none. My strongest attack, an under-specified signature contract read only from digests, fails on correctness. The design already treats the webhook as a signal and takes truth from an authenticated re-read plus a poll. The vendor prescribes this (Monitoring A, GetOneOffPayment A), and the contract forces it: there is no event id, delivery is unordered, and every lane graded that finding A. BORROW, TRAP or DEFER would fix none of the gaps found. Carry these binding conditions into DR-003's Risks/Caveats and the architecture creative: (1) key-id allow-list and URL-encoding, single-flight fetches, negative cache, fetch cap, and 5xx on a transient key-fetch failure; (2) reconcile is not a resolution path for BANK_ERROR_INDETERMINATE, which the apply step routes to DR-004's hold branch (U4/MVE-004); (3) the attempt is correlated by the stored `_payment` only, and `webhook_uri` params are never authoritative. MVE-005 stays a build-gate prerequisite.
- **confidence note**: run on Opus (no model fallback). The source re-checks were WebFetch digests, not raw bytes.

  - *Why the attack does not disqualify.*

    - (c) The re-checked one-off overview lists "Accounting software uses one-off payments as a simple way to accept invoice payments" as a use case. In that case the software vendor is not the payee and collects for its own customers, which is the same shape as a platform collecting for teams. This is A-grade support that the third-party-payee pattern is intended. It is not a contractual guarantee.
    - (d) The one-way steps (contract signature, Tier 1 review, ADR 0020 made binding) all come after MVE-001, which gates them: nobody signs without the payee clause. Phases 1-3 run behind the gateway port and fake adapter (task file line 581), so the near-term commitment can be reversed.
    - (e) No shape that fits ADR 0016 has better evidence. DRP-002 finds every alternative is either merchant-of-record or settles to the platform, and enduring `/payments` is a TRAP. DEFER would leave the plan without a default while changing nothing about the gating that already exists.
  - *Conditions this Upheld depends on (carry into DR-001 and the Phase 4 human gate).*
    1. A written U1 answer is a hard precondition for every one-way step: the contract, ADR 0020 Accepted, and the Phase 4 live-adapter build.
    2.     3. If U1 brings a liability term, the human gate must rule on verifying payee details at save time (ADR 0016:24 does not do this today) before ADR 0020 is accepted.
    4. If U1 is negative, DR-001 becomes DEFER (U10/U11) and must not stay ADOPT.
- **disposition**: Upheld
- **required_revision**: none. The verdict depends on the conditions above: a written U1 confirmation that covers liability, new-payee holds and payee caps must come before every one-way step, and a negative U1 re-grades DR-001 to DEFER.
